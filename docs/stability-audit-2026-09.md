# 방송 안정성 순차 점검

## 진행 규칙

- 2026-09-20 사용자 요청: 자동 점검·매시간 예약을 만들지 않는다. 이후 단계는 사용자 요청 시에만 진행한다.

- 한 차례에 작은 수정 묶음 하나만 구현, 검증하고 결과를 보고한다.
- OBS 설치본과 방송 설정은 변경하지 않는다. 무중단·무결함을 보장한다고 표현하지 않는다.
- 각 단계 시작에 사용량을 확인한다. 제한에 근접하면 변경사항과 다음 행동을 이 문서에 기록하고 새 작업을 시작하지 않는다.
- 검증하지 않은 DLL은 배포하지 않는다. 빌드한 배포물은 플러그인만 포함한 ZIP으로 제공한다.
- 사용량 리셋 크레딧은 사용자 추가 승인 없이 사용하지 않는다.

## 단계

1. 완료: 저장소의 대량 이동·폴더 해제 최적화, 캔버스 조회 실패 시 초기화 보호 및 회귀 테스트 (1.0.11).
2. 대기: OBS 로드·언로드, 장면 모음 교체, 저장 타이머와 이벤트 재진입 검토.
3. 대기: JSON 로더와 실행 취소·복원 입력 제한 및 데이터 보존 검토.
4. 대기: 트리 재구성·다중 선택·드래그·모달 창 경로 검토.
5. 대기: 남은 소스와 빌드 설정 검토, 회귀 테스트, 최종 배포 정리.

## 1차 Plan / Do

`dissolveFolder`와 `moveNodes`는 항목 하나마다 vector에 삽입하여 뒤쪽 요소를 반복 이동한다. UI 스레드에서 큰 목록을 조작할 때 불필요한 작업량이 증가한다.

삽입을 move iterator를 사용한 범위 삽입으로 바꾼다. 장면 순서, 객체 정체성, 별칭·색상, OBS 원본 동작은 유지한다. moveNodes의 원본 삭제 반복은 이번 범위에서 변경하지 않는다.

## 1차 Check / Act

캔버스 목록을 조회하지 못한 `resetToLive({})` 호출은 기존 배치를 보존하도록 수정했다. 정상 캔버스에 장면이 없는 경우의 초기화는 계속 허용한다. 드라이브 복구 후 미적용 상태를 확인하고 소스와 테스트에 함께 반영했다.

- 하위 에이전트가 추가한 1만 항목 이동·폴더 해제 및 혼합 선택 회귀 테스트를 검토했다.
- 드라이브 중단 시 생성된 CTest 파일에서 NUL 바이트 손상을 확인했다. 소스는 유지하고 새 빌드 디렉터리에서 재검증했다.
- `build_tests_recovery`: 전체 CTest 통과 (1/1, 5.76초).
- `build_x64_recovery`: Windows x64 RelWithDebInfo 빌드 성공. OBS 개발 라이브러리 빌드도 재생성했다.
- `release/scene-tree-view-1.0.11-windows-x64.zip` 생성 및 포함 DLL SHA-256 일치 확인.
- 설치된 OBS, 방송 설정, GitHub 게시물은 변경하지 않았다. 실제 OBS UI·장시간 방송 테스트는 미실시다.

## 후속 확인 후보 (아직 확정 결함 아님)

- `frontendSaveLoad`의 일반 로딩 경로는 백업 복원과 달리 깊이·노드 수 제한이 없다.
- `fromJson`은 파싱 성공을 확인하기 전에 기존 데이터를 지운다. 컬렉션 간 데이터 혼입 방지와 실패 보존을 함께 설계해야 한다.
- 컬렉션 cleanup에서 저장 타이머와 queued rebuild 처리 순서를 확인해야 한다.
- 모듈 언로드 시 dock 소유권과 bridge 콜백 수명 순서를 OBS 구현과 대조해야 한다.

## 재개 지점

사용자가 재개를 요청하면 2차만 진행한다. 1차(1.0.11)는 완료됐으므로 이전 드라이브 중단 안내를 근거로 다시 구현하지 않는다. 정상 빌드 경로는 `build_x64_recovery`, 테스트 경로는 `build_tests_recovery`다.
